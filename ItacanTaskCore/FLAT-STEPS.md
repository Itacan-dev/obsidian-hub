# Flat native Steps

A Task owns an ordered list of Steps. Each Step has a stable UUID, title/body, completion state and native clocks. Order is independent of identity. Completing or reopening a Step never completes or reopens its Task. Recurring Tasks retain their existing rules, occurrence identities and completion ledger.

Application actions compile through the existing native writer into TaskCore commands. Step add/edit/complete/reopen/delete/reorder and atomic rich creation/Save use the same revision, inventory, receipt and publication guards. Full drafts explicitly retain or delete every old Step; deletion names one UUID. There is no reparent action, subtree deletion, depth, parent selector or recursive ordering in product models.

## Immutable evidence boundary

The v1 task/storage/wire shape still has a parentStepId slot; new Steps store null. Recurrence evidence similarly retains parentNodeId:null. Existing atomic wire commands retain null ancestry and false/empty deletion fields where the intent compiler emits the original signed vocabulary. The historical expectedTreeDigest/treeDigest names hash the exact Step list; they do not build a tree. Changing these signed bytes or their meanings would break prior receipts and synchronization proofs.

historical-step-evidence.js contains only validation and replay interpretation for old nested records. Personal v1/v2 and Git/N4 proof validators enable that internal replay context after their existing signature/provenance checks. It is never accepted from an application command or wire payload. Fresh local commands reject nesting, reparenting and cascade deletion. Historical nested tasks remain verifiable and explicitly unavailable for editing; they are never flattened or migrated silently. No current enrolled Work authority contained nested Steps or recurrence template nodes at this change's baseline.

The synthetic signed fixtures under tests/fixtures/step-evidence-v1 were generated by the preserved pre-change software, not by the new implementation. Their pinned hashes test nested creation, reparenting, reordering and cascade evidence. Flat-operation tests replace the old hierarchy feature tests; normal-operation tests make historical traversal throw if called.

No repository migration, identity change, receipt rewrite, new synchronization protocol or Markdown task path is introduced. Current native consumers continue to use stable Task/Step IDs. Historical source-envelope ancestry describes original evidence only and is not a Step editor or creation feature.
