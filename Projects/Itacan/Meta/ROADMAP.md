## Product Development

### September 2026 — Obsidian Prototype

Complete the Obsidian implementation of Itacan, including the Hub and **Atlas**. The objective is to establish a functional prototype that can be used continuously until the standalone application is available.

The prototype should be sufficiently complete to validate core workflows, interaction patterns, terminology, and product structure. Development after September should be limited primarily to fixes or changes that provide useful information for the standalone product.

Move the prototype to Github.

### October 2026 — Onboarding and Guided Setup

Design the initial onboarding experience for new users.

The onboarding flow should:

- introduce Itacan and its core concepts concisely;
    
- identify the type of work or Project the user intends to undertake;
    
- guide the user through initial Workspace setup;
    
- recommend relevant applications to permit;
    
- allow the user to add their own applications;
    
- recommend relevant websites;
    
- establish the initial website and application whitelist;
    
- introduce the user to the principal Itacan workflow without requiring a comprehensive feature tutorial.
    

The objective is to move a new user from installation to a usable working environment with minimal configuration burden.

### November 2026 — Theme System

Design the application-wide **Theme System**.

Themes should function as complete visual configurations rather than simple color schemes. A Theme Pack may define:

- colors;
    
- typography;
    
- buttons and controls;
    
- panels;
    
- backgrounds and cover images;
    
- borders and surfaces;
    
- icons and supporting imagery;
    
- other application-wide visual properties.
    

The underlying system should be designed so that themes can be changed consistently across the entire application without altering functionality.

### December 2026 — Build-Ready Specification

Complete the specification required to build the standalone application.

This should include:

- complete functionality documentation;
    
- finalized interface designs and visual references;
    
- application architecture;
    
- component and data architecture;
    
- coding and design principles;
    
- Codex prompts and implementation instructions;
    
- agent definitions and responsibilities;
    
- acceptance criteria;
    
- test requirements;
    
- required assets;
    
- unresolved implementation decisions.
    

The objective is to enter January with the product specified closely enough that implementation can focus on execution rather than product design.

### January 2027 — Standalone Application and Internal Alpha

Build the standalone Itacan application from the completed specification.

The first implementation should integrate the major systems into a coherent application rather than treating each feature as an isolated prototype.

By the end of January, the application should reach **Internal Alpha**: all core functionality is present and sufficiently integrated for systematic internal testing, while defects and incomplete refinements remain expected.

### February 2027 — Stabilization and Closed Beta

Shift development from feature implementation to stabilization.

Primary work should include:

- bug fixing;
    
- regression testing;
    
- performance optimization;
    
- reliability improvements;
    
- installation and update testing;
    
- platform integration;
    
- usability refinement;
    
- consistency with the product specification.
    

Once the application reaches sufficient stability, distribute it as a **Closed Beta** to a limited group of external users.

The objective is to finish February with a release candidate suitable for preparation toward v1.0.

## Product Validation

Product validation should begin before the standalone application is built.

From September onward, the Obsidian prototype should be used to identify:

- workflows that are genuinely useful;
    
- features that create unnecessary friction;
    
- missing functionality;
    
- confusing terminology;
    
- interaction patterns that do not work in sustained use;
    
- assumptions that should be reconsidered before implementation.
    

External validation should gradually supplement internal use.

During the Closed Beta, feedback should be collected from users who were not involved in designing Itacan. At least part of the beta cohort should belong to the intended target audience rather than consisting exclusively of friends or acquaintances.

Feedback should distinguish between:

- defects;
    
- usability problems;
    
- missing functionality;
    
- feature requests;
    
- onboarding problems;
    
- misunderstandings of the product;
    
- broader product-positioning issues.
    

## Market Research and Positioning

Market research should begin in **September 2026**, before active promotion.

Initial work should focus on:

- competing and adjacent products;
    
- existing workflows used by the target audience;
    
- recurring user problems;
    
- reasons users adopt or abandon comparable products;
    
- differentiation;
    
- market terminology;
    
- potential acquisition channels.
    

The initial target audience should be narrowed sufficiently to identify a practical first market rather than attempting to market simultaneously to every potential user group.

By November and December, this research should result in a clear description of:

- the initial target customer;
    
- the principal problem Itacan addresses;
    
- the primary use cases;
    
- the product's differentiating characteristics;
    
- the language used to communicate its value.
    

## Marketing and Go-to-Market

Marketing should develop in stages alongside product maturity.

### September–October — Customer Discovery

Focus on research rather than promotion.

Activities should include:

- user interviews;
    
- competitor analysis;
    
- workflow research;
    
- testing product descriptions and terminology;
    
- identifying promising initial user segments.
    

### November–December — Pre-Launch

Begin establishing a public presence once the product concept and positioning are sufficiently defined.

This may include:

- an Itacan website or landing page;
    
- product descriptions;
    
- screenshots and demonstrations;
    
- an early-access or beta sign-up;
    
- initial communication through relevant communities;
    
- recruitment of Closed Beta participants.
	
- register on KTH innovation at end of November
    

The objective is to establish awareness and recruit suitable early users rather than maximize reach.

### January — Controlled Pre-Launch

Marketing should remain limited while the standalone application is in Internal Alpha.

Communication may continue with prospective beta users, but broad user acquisition should not begin before the application is stable enough to provide a representative experience.

### February — Closed Beta and Launch Preparation

Use the Closed Beta to validate both the product and its positioning.

Prepare:

- launch messaging;
    
- product demonstrations;
    
- website content;
    
- onboarding material;
    
- documentation;
    
- pricing pages;
    
- support material;
    
- initial launch channels.
    

Broader acquisition should follow only once beta feedback has been incorporated and the product is ready for v1.0.

## Closed Beta

The Closed Beta should consist of a limited number of users who can use Itacan under normal conditions without close supervision.

Participants should include:

- trusted friends or acquaintances who can provide detailed feedback;
    
- users who match the intended target market;
    
- users unfamiliar with the internal design process.
    

Beta users should receive the complete product experience wherever practical rather than a heavily constrained demonstration version.

The beta should evaluate:

- installation and first-run experience;
    
- onboarding;
    
- comprehension of Itacan's concepts;
    
- everyday Workspace use;
    
- Atlas;
    
- Tasks;
    
- The Oath;
    
- reliability and performance;
    
- continued use over time;
    
- reasons for discontinuing use;
    
- perceived value.
    

Feedback should be recorded systematically and converted into identifiable product changes rather than handled only through informal comments.

## Pricing and Packaging

Pricing should be developed in two stages.

### December 2026 — Pricing Hypothesis

Define the provisional commercial model, including:

- plan structure;
    
- proposed prices;
    
- functionality included in each plan;
    
- project and storage limits;
    
- collaboration features;
    
- personalization;
    
- cloud services;
    
- AI-related functionality where applicable.
    

The existing Free, Light, and Pro concept should remain a hypothesis until tested with external users.

### February 2027 — Launch Pricing

Use market research and Closed Beta feedback to finalize:

- plan names;
    
- monthly and annual pricing;
    
- feature allocation;
    
- free-plan limitations;
    
- storage allowances;
    
- collaboration capabilities;
    
- upgrade incentives.
    

Pricing should be settled before the public release, but only after sufficient evidence has been gathered from prospective and actual users.

## Public Release

The public release should follow the Closed Beta rather than occur simultaneously with it.

The target sequence is:

**Obsidian Prototype → Build Specification → Internal Alpha → Closed Beta → Release Candidate → v1.0**

A public v1.0 release may therefore follow in **March 2027**, provided that the February beta does not reveal issues requiring another stabilization cycle.
